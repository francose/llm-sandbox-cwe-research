\begin{abstract}
Large language models increasingly generate C code that is compiled and run inside
sandboxes trusted to contain untrusted behaviour, and that trust rests on a stack of
commodity defences: compiler warnings, static analyzers, build-time hardening, and
sanitizers. This paper measures, for the specific class of spatial memory corruption,
which of those defences actually fire and whether model-generated C lands in the gaps they
leave. We point ten independent commodity detectors at six memory-corruption classes and
find that one class, \emph{intra-object} (adjacent-field) overflow, is missed by every
detector, including AddressSanitizer and Valgrind, because the write stays inside a single
valid allocation and crosses no boundary. The gap is not a toolchain artifact: it holds
across five compilers, two \texttt{\_FORTIFY\_SOURCE} levels, AddressSanitizer under two
back-ends, and two CPU architectures. We then give three local code models \Ntotal{}
security-neutral fixed-buffer tasks and check every generated snippet against a single
translation-unit, AddressSanitizer-backed oracle calibrated on golden-safe and
golden-vulnerable references. \Nvuln{} of \Nusable{} usable snippets contain a confirmed
spatial overflow, concentrated in the smallest model, and the commodity static stack
diagnosed the overflow in \StaticDiag{} of the \Nvuln{}. We connect the results at the
detection-layer level: the shipped static layer catches none of these generated overflows,
and the shipped runtime tool is blind to the intra-object subclass, so neither layer is a
sufficient detector for the class. We report every number with its limits, including why
the rate is a lower bound and a false positive removed by hand-verification.
\end{abstract}

\section*{Introduction}

For decades, memory-safety bugs have been the largest single category of serious software
vulnerabilities. Out-of-bounds write (CWE-787) and out-of-bounds read (CWE-125) sit near
the top of the MITRE CWE Top 25, and vendor data has long attributed roughly two-thirds of
critical vulnerabilities to memory errors. A new pressure has been added to this old
problem: code produced by large language models is now compiled and executed by automated
agents, often inside a sandbox that is trusted to hold the line if the generated code turns
out to be unsafe.

That trust is the subject of this paper. When an LLM-driven agent compiles and runs its own
C, the sandbox has to hold at the memory boundary inside the process, and the tools we rely
on there are a specific, commodity stack: the compiler's warnings, the static analyzers run
in CI, the hardening flags baked into the build, and the sanitizers used in testing. We do
not ask whether a model is ``capable'' of writing an exploit. We ask which memory-safety
weaknesses survive that commodity stack, and whether the code a model actually generates
falls into the surviving classes.

The question we set out to answer:

\begin{quote}
\emph{For spatial memory corruption, which commodity detectors actually fire per bug class,
and does model-generated C land in the classes they miss?}
\end{quote}

What this paper contributes:

\begin{enumerate}[leftmargin=1.6em]
  \item A per-detector coverage map of ten commodity detectors against six
        memory-corruption classes, identifying \emph{intra-object} (adjacent-field)
        overflow as a total detection gap: missed by every static analyzer, every compiler
        warning set, build-time hardening, and both major sanitizers.
  \item Evidence that the gap is structural rather than incidental: it holds across five
        compilers, two \texttt{\_FORTIFY\_SOURCE} levels, AddressSanitizer under two
        back-ends, and two CPU architectures.
  \item A measured study of whether three local code models produce this class on ordinary
        fixed-buffer tasks, using an automated, calibrated, hand-verified ground truth, and
        of how much of what they produce the commodity static stack can see.
  \item An honest account of the limits, including a false positive removed by
        hand-verification, a lower-bound rate, and the single-shot scope.
\end{enumerate}

\section*{Background}

\subsection*{Spatial memory safety}
A spatial memory-safety violation reads or writes outside the bounds of an object. The two
canonical forms are out-of-bounds write (CWE-787) and out-of-bounds read (CWE-125). In C,
nothing in the language enforces bounds, so safety rests on programmer discipline and on the
external tools examined here.

\subsection*{Intra-object versus boundary overflow}
The distinction this paper turns on is where the overflow lands. An \emph{allocation-boundary}
overflow writes past the end of a heap or stack object; red-zone tools (AddressSanitizer)
and shadow-memory tools (Valgrind) detect it because the write crosses into instrumented
memory. An \emph{intra-object} overflow writes past one struct field into an adjacent field
of the \emph{same} allocation:

\begin{lstlisting}
struct rec { char name[16]; int uid; }; /* one allocation */
strcpy(r->name, attacker_input);        /* 20 bytes: name[16] overrun spills into uid */
\end{lstlisting}

No allocation boundary is crossed, so boundary-based tools stay silent by construction.
Field boundaries exist only at the ABI/type layer, one granularity finer than any commodity
mechanical control operates at, which is the structural reason for the gap.

\subsection*{The commodity detection stack}
We treat each of the following as an independent \emph{detector} and ask, per class, whether
it fires. Static and compile-time: gcc \texttt{-Wall -Wextra}, gcc \texttt{-fanalyzer}, gcc
link-time type checking, clang warnings, the clang static analyzer, and cppcheck. Runtime:
\texttt{\_FORTIFY\_SOURCE}, AddressSanitizer (ASan), UndefinedBehaviorSanitizer, and
Valgrind/Memcheck.

\subsection*{Operational states of a run}
For a build that exercises a bug on a given input, we classify the outcome by direct
evidence (exit signal, emitted diagnostic, and a self-check the probe prints): \textbf{silent}
(corruption confirmed, exit 0, no diagnostic; exploitable and undetected), \textbf{detected}
(a defense named the error and stopped it), \textbf{crashed} (a raw fault with no diagnostic;
denial of service, not detection), \textbf{prevented} (the unsafe op refused before
corruption), and \textbf{clean} (the bug did not take effect). These are defined so that
``missed'' is evidence rather than opinion; a crash is deliberately not counted as a
detection.

\section*{Related Work}
AddressSanitizer~\cite{asan} and Valgrind/Memcheck~\cite{valgrind} are the red-zone and
shadow-memory tools whose boundary model is precisely why intra-object overflow is invisible
to them. The closest prior art on the intra-object case is ASan's own field-padding
extension~\cite{asanintra}, which inserts poisoned padding between fields to catch
adjacent-field overflow, but only for C++ non-standard-layout classes, behind an experimental
flag, and in no shipped build; that scoping is why the practical gap stands.
\texttt{\_FORTIFY\_SOURCE}~\cite{fortify} provides the build-time object-size checks we
measure at the shipped-hardening layer. A separate line of work reports that code models
generate insecure code; Pearce et al.~\cite{copilot} found roughly 40\% of Copilot
completions across 89 security-relevant scenarios were vulnerable. Our contribution is not
that claim but its connection to a measured, toolchain-general detector gap.

\section*{Threat Model}
By ``sandbox'' we mean the commodity stack normally trusted to hold the line around
compiled-and-executed code: the compiler and its hardening flags, the static analyzers run in
CI, and the sanitizers used in testing. The adversary is not assumed to be external; the
unsafe C may arrive because a model was manipulated or simply because it generated a bug. The
asset at risk is process integrity at the memory boundary. A defense ``holds'' for a class if
some detector moves the outcome out of the \textbf{silent} state. The central question is
which classes remain \textbf{silent} under the shipped configuration, since a silent outcome
is exploitable and undetected.

\section*{Methodology and Experimental Setup}

We test three falsifiable hypotheses. The first, the \emph{coverage hypothesis}, is that the
commodity detection stack covers spatial memory corruption. The second, the
\emph{toolchain-generality hypothesis}, is that any gap the first finds is an artifact of a
single compiler or version. The third, the \emph{generated-code hypothesis}, is that
model-generated C both produces the class and is caught by the static stack. Each is set up
below and tested in the Results; as stated, each is falsified.

\subsection*{The coverage hypothesis}
We point all ten detectors at each of six classes and record CAUGHT versus MISSED, saving
raw per-cell evidence. Each class is a minimal probe with a self-check that prints
\texttt{outcome=corrupted|clean}. Each runtime detector is built with isolation flags so the
column measures exactly one tool (canary and \texttt{\_FORTIFY\_SOURCE} disabled when
measuring a sanitizer, and so on). A catch is recorded only when a memory-safety diagnostic
names the defect (static) or the tool's own runtime signature fires; compiler meta-noise such
as ``unknown warning option'' is filtered so it can never count as a catch. We measure each
detector in isolation rather than as a combined pass because the claim of interest is
\emph{which} layer is blind.

\subsection*{The toolchain-generality hypothesis}
We re-run the six classes through five compilers (gcc-11, gcc-12, clang-14, clang-15, tcc),
\texttt{\_FORTIFY\_SOURCE} levels 2 and 3, and ASan from both gcc and clang, and compare
against a companion aarch64/gcc-15 environment. The gap holds if intra-object stays a total
gap and no compiler or level newly catches it.

\subsection*{The generated-code hypothesis}
We give three local models (qwen2.5-coder:1.5b, deepseek-coder:6.7b, qwen2.5-coder:7b)
\Ntotal{} security-neutral fixed-buffer tasks (18 tasks, 4 samples each), asking for a struct
with a fixed \texttt{char} field filled from variable-length input, with no security framing.
Ground truth is a \emph{single-translation-unit} oracle: the test driver is concatenated with
the model's snippet so it binds to the model's own struct and function, and any layout
deviation becomes a compile error counted as \texttt{compile\_fail} rather than silent
undefined behaviour. Under ASan we sweep input lengths and apply two oracles: Oracle~A
(allocation-boundary overflow, via ASan) and Oracle~B (an intra-object sentinel on a trailing
scalar). Every one of the 18 drivers is calibrated against a golden-safe (\texttt{strncpy}
plus explicit null) and golden-vulnerable (\texttt{strcpy}) reference before any model code is
judged; all 18 passed. Every flagged case is hand-verified.

\subsection*{Environment}
All experiments ran on Ubuntu 22.04.5 (x86\_64, WSL2 kernel 6.18) with gcc-11.4/12.3,
clang-14/15, cppcheck 2.7, valgrind 3.18.1, and tcc 0.9.27; models served locally via ollama.

\section*{Case Studies}
The six classes exercised by the coverage and toolchain-generality hypotheses:

\begin{itemize}[leftmargin=1.4em]
  \item \textbf{Intra-object out-of-bounds write (CWE-787).} An unbounded copy overruns a
        \texttt{char} field into an adjacent field of the same struct. The load-bearing case.
  \item \textbf{Heap out-of-bounds write (CWE-787).} The same overrun past the whole
        heap allocation.
  \item \textbf{Stack out-of-bounds write (CWE-787).} The overrun past a stack buffer.
  \item \textbf{Use-after-free (CWE-416).} A write through a pointer to freed memory.
  \item \textbf{Integer-overflow allocation (CWE-190).} A size computation wraps, producing
        an undersized allocation later overrun.
  \item \textbf{ABI/type skew (CWE-843).} Two translation units disagree on a struct's type,
        so a field write lands at the wrong offset.
\end{itemize}

\subsection*{Toolchain generality}
No compiler warned on intra-object at any level; the shipped state is silent under
\texttt{\_FORTIFY\_SOURCE} 2 and 3; ASan misses it under both gcc and clang; the gap holds
across two architectures and gcc versions 11, 12, and 15. One honest side-finding: gcc-12
emits a compile-time use-after-free warning where gcc-11 is silent, which is real but
orthogonal to intra-object.

\subsection*{Generated-code study}
Of \Ntotal{} generations, \Nusable{} compiled against the oracle (\Ncfail{} were contract
deviations). \Nvuln{} of \Nusable{} usable snippets contain an ASan-confirmed spatial
overflow, an overall rate of \RateAll{} (95\% CI \RateAllCI{}), dominated by model size
(Table~\ref{tab:h3}). No member of the commodity static stack diagnosed the actual overflow
in any of the \Nvuln{} confirmed cases: \StaticZero{} drew no diagnostic at all, and the rest
drew a warning about a different defect. These are input-length-dependent writes in a function
the analyzer sees in isolation, which is undecidable at compile time; only runtime ASan caught
them, and ASan ships in no build here. We did not observe an ASan-invisible intra-object case
in generated code: the one candidate our sentinel oracle flagged was a false positive, a
function that legitimately assigns its trailing field, removed by hand-verification.

\section*{Observations}
The three results connect at the layer level rather than by asserting more than we measured.
The shipped \emph{static} layer caught none of the \Nvuln{} generated overflows; the coverage
and toolchain-generality results show the shipped \emph{runtime} tool (AddressSanitizer) is
blind to the intra-object subclass;
so neither layer is a sufficient detector for the class. One generated overflow
(\texttt{parse\_kv}) makes the boundary concrete: its ASan report shows the write reaching the
allocation boundary only after passing \emph{through} an adjacent field, so a bounded version
of the same code would be the intra-object probe, invisible to ASan. A second observation cuts
against intuition: in the generated-code study the smallest model was the most memory-unsafe, the reverse of a naive
``bigger is always worse'' expectation, so memory-safety carefulness is its own axis.

\section*{Recommendations}
A pipeline that compiles and runs LLM-generated C should not treat a clean compile, clean
static analysis, or even a clean AddressSanitizer run as evidence that adjacent-field overflow
is absent. Detecting this class needs an oracle that reasons about struct-field boundaries
rather than allocation boundaries: ASan field-padding on recompiled structs, a bounds-checking
build, or hardware sub-object bounds where available. Where none is available, the safest
posture is to treat fixed-size struct fields filled from variable-length input as a review
target in generated code, since that is the exact shape the detectors miss.

\section*{Limitations}
The generated-code rate is a lower bound: the intra-object oracle cannot see mid-struct overflows, the
multi-field tasks are judged by the boundary oracle alone, and one excluded compile-fail
contained an unbounded copy, all of which can only raise the true rate. The oracle's
intra-object check produced one false positive (a function that legitimately writes its
trailing scalar), caught by hand-verification; the confirmed rate rests on AddressSanitizer.
The rate is conditional on fixed-buffer tasks and on the provided interface, is measured on
three small open-weight models on one machine, and reflects single-shot generation rather than
a multi-turn agent. One toolchain per version was used; the intra-object result is structural
and the toolchain-generality result spans two architectures, but the broader matrix should be
re-run elsewhere. A non-default
ASan build with intra-object red zones can catch some of these overflows but is C++-oriented,
opt-in, and part of no shipped build, so the practical gap stands.

\section*{Conclusion}
Spatial memory corruption has a specific, reproducible blind spot, intra-object overflow, that
no commodity detector catches and that survives five compilers, two hardening levels, both
sanitizer back-ends, and two architectures. Small code models produce spatial overflows on
ordinary fixed-buffer tasks at a measurable rate, and the shipped static layer diagnosed none
of them. Read at the layer level, the static layer misses input-dependent overflow in isolated
functions and the runtime layer misses the intra-object subclass, so the default stack is not
a sufficient detector for this class. Closing the gap requires field-boundary reasoning that is
not in the default stack today.
